# 栏目：系统控制类技术文

项目只是解剖对象。要同时完成：看懂当前系统 + 可迁移模型 + 会指导 Agent 实现。

读者能读代码，痛点是「每段都懂，不知道为什么这样拆」。重点从 How 挪到 Why / 责任住在哪 / 怎么协作 / 换掉会怎样。

## 选题

```
一个目标 + 一个现实约束 + 一个原始方案开始失效 = 一篇
```

禁止以术语开题。先找系统困难。

## 延迟揭晓

本文要教的新名词：不得出现在标题、封面、Hook、第一个问题阶段。前半篇只用功能描述。后部才说「这种机制通常被称为 XXX」。

## 默认主线（可裁剪，不可反过来）

真实困难 → 最小可工作 → 看似没问题 → 加真实约束 → 原设计混乱 → 拆责任 → 稳定边界 → 看三流 → 比较另一种设计 → 代码证明 → 换部件验边界 → 回到完整 Runtime → 正式命名 → 迁移。

必须保持：问题推动概念出现。

## 第一屏

1. 熟悉现象  2. 隐藏矛盾  3. 本文只解决一个问题。

Hook 制造解释缺口，不要震惊体。

## 最小错误版本

先给 naive 实现，再施压（换模型 / 工具变多 / 重启 / 失败 / 权限 / 远程 / 并发 / 可观察）。每一压只暴露一个边界。

## 代码

只证明概念存在、暴露边界、或让读者改一处做实验。禁止逐行翻译。代码后必须用：

> 当【事件】发生时，【主体】读取【状态】，把控制权交给【能力】，产生【结果】，进入【下一处】。

图一次只回答一个问题，逐层生长。需要时拆 Control / Data / State / Capability，不要混在一张图。

## 案例

最小但真实：2 工具→50；本地 Shell→Docker；不崩溃→恢复。不要一上来完整 AI IDE。
